# 【待执行】EXP-DEC-INFO-PROBE：解码器有没有"缺信息"？候选条件化风险选邻居有没有用？

- 类型：探索性实验，沿用 EXP-SET-INTERACT-PROBE 的冻结缓存框架。B0 冻结，只训练很小的修正模块。
- 预计耗时：缓存比上次大，加入了编码器 token 和邻居位置；建缓存约 5–10 分钟。修正模块训练 6 臂 × 3 seed 共 18 次，预计约 30–40 分钟，是上次的 1.5–2 倍。
- 状态：只有设计文档，代码待写。

## 1. 为什么做

【已完成】EXP-SET-INTERACT-PROBE 说明：
- B0 的 20 条候选已经充分分散，有效候选 19.75 / 20；
- 但仍有 27% 的窗口没被覆盖。只看沿朝向"走多远"时几乎都有候选覆盖到，**漏的是二维位置的组合**：距离对了的那条候选，横向偏了。

而 h3 解码器有一个明显的信息瓶颈：**20 个模式读到的是同一个上下文向量**。它由目标自己的最后 token、平均 token 和 7 维运动特征压缩而成。往左和往右的模式拿不到任何不同的信息，比如"左边有没有人挡着"。

本实验回答两个问题：
1. **解码器是不是缺信息？** 让每条候选额外读取更多编码器信息，看能否明显超过"自我修正"。
2. **"候选条件化风险选邻居"这个具体设计有没有用？** 对每条候选，沿它自己的未来路径计算和邻居的 TTC/DCA，选出风险最高的几个邻居，并和"按当前距离选邻居"比较。

这对应论文里要讲的主线：**运动学风险驱动的稀疏交互，编码器用在历史上，解码器用在每条假设的未来上。**

## 2. 和已有工作的关系（初步检索，写代码前还要再查）

- 最接近的是 NaviAIS（2026，船舶）：它对每条候选和邻居的预测轨迹计算交互风险，但**风险只用来给候选打分排序**，不用于选邻居和修正候选。
- 有一些车辆方法用二维 TTC 从**当前状态**筛选高影响邻居，所有候选共用一套邻居。
- 候选读取邻居信息的做法（LGCMT、Group Query 的 Q2A、MRGTraj 的 Social Refiner）都是稠密注意力，或者对所有候选一视同仁。
- 目前没检索到"按每条候选的未来路径计算 TTC/DCA 来稀疏选邻居，再做轻量修正"的行人工作，但只做了初步检索。

## 3. 设置

### 3.1 底座和数据（与上一个实验相同）

- 底座：B0@64 seed 42（`E1C_E64_s42`），固定最终 EMA 权重，全部冻结。
- 训练用 C0 fit（21,719 窗口），评价用 C0 dev（4,753 窗口）。不碰任何测试集。dev 已被反复使用，因此属于探索。
- 上一个实验的缓存保留不动，它只有修正模块需要的字段。本实验新建一份缓存，**额外保存**：
  - `tokens_self`：目标 8 个时间步的编码器 token，[8, 96]，float16；
  - `tokens_nbr`：每个邻居最后一步的编码器 token，[8, 96]，float16；
  - `nbr_pos`、`nbr_vel`：邻居在**目标朝向坐标系**下、相对目标最后观测点的位置，以及最后一步的速度（m/s，`(p[-1]−p[-2]) × 2.5`，与编码器的 `ttc_dca_graph` 一致）；
  - `nbr_valid`：邻居是否有效，来自 num_valid。
- 缓存校验：
  - 用缓存重建的候选与保存的 B0 预测之差 ≤ 1e-4（与上次相同）；
  - 邻居坐标系一致性检查：目标自己在同一坐标系下的最后位置必须为 0，朝向必须为 +x。
- 体积估算：fit 约 21,719 × (8 + 8) × 96 × 2 B ≈ 67 MB，另加几何字段，规模很小。

### 3.2 候选条件化风险（C3 用，完全不看真值）

对每个窗口、每条候选 k（第一遍、修正前的轨迹 P_k(t)，t = 1…12，每步 0.4 s）和每个有效邻居 j：

1. 邻居按匀速外推：Q_j(t) = p_j + v_j × 0.4t；
2. d_kj(t) = ‖P_k(t) − Q_j(t)‖；
3. DCA_kj = min_t d_kj(t)；TTC_kj = (达到最小距离的步数) × 0.4 s；
4. 风险分数**照搬编码器 `ttc_dca_graph` 的形式和常数**：
   r_kj = exp(−TTC_kj / 2.5) · exp(−DCA_kj / 1.25) + 0.10 · exp(−d0_j / 3.0)，其中 d0_j 是当前距离；
5. 有效条件也照搬：DCA_kj < 3.0 m（TTC 在 0–4.8 s 之间，自然满足 < 6 s）；
6. 每条候选取风险最高的 m = 3 个有效邻居；不足 3 个就取实际个数，没有就只读自身 token。

所有常数都来自编码器，**运行前固定，不调**。

### 3.3 六个训练臂

所有 C 臂的结构完全相同：

1. 先做与 A1 相同的"只看自己"修正块；
2. 再接一个交叉注意力块：Q 来自候选 token，K/V 来自该候选可读的上下文 token（96 → 24 投影），加上关系特征经小 MLP 得到的注意力偏置；
3. 然后 FFN，输出有界的锚点修正和得分修正。

修正量和输出部分与 A1 完全一致：MAX_SHIFT = 0.30 × 尺度，零初始化，所以初始时与 B0 逐位相同。

| 臂 | 每条候选额外能读到 | 关系偏置特征 | 回答什么 |
|---|---|---|---|
| A0 | 无（冻结 B0） | — | 基准 |
| A1 | 无，只做自我修正 | — | 与上次 A1 相同；检查代理是否可复现 |
| A1L | 无，但加宽 FFN，使参数量与 C 臂相同（±5%） | — | 容量对照：增益是不是只来自参数变多 |
| C1 | 目标自身 8 步 token | 时间步编号 embedding | 历史细节是否被压缩掉了 |
| C2 | C1 + 所有有效邻居 token（稠密） | 当前相对位置、相对速度、距离 | 社交信息的上限 |
| **C3** | C1 + **按候选路径风险**选出的 ≤3 个邻居 | 该候选与该邻居的 DCA、TTC/4.8、d0、最近点相对位置 | **本实验的设计** |
| C4 | C1 + 按**当前距离**选出的 ≤3 个最近邻居（所有候选相同） | 当前相对位置、相对速度、距离 | 普通的稀疏选邻居 |

- C3 和 C4 读取的邻居数量相同，结构相同，**只有"怎么选邻居"和"关系怎么描述"不同**。
- C2 和 C3 比较的是"稠密 vs 稀疏"。

### 3.4 训练（与上一个实验相同，便于直接对照）

- 损失：只用 B0 原损失。上次的再分配损失已证明无效，不再使用。
- AdamW 学习率 1e-3，wd 1e-4，batch 256，cosine 衰减到 0，20 轮，不早停，取第 20 轮。
- 3 个修正模块 seed（0、1、2）。同一 seed 下各臂的共享部分初始化相同，数据顺序也相同。
- 一共 6 臂 × 3 seed = 18 次训练。

## 4. 零训练前置诊断 D0（描述用，不设门槛）

在缓存上直接统计，不看真值：
- 每个窗口有效邻居数的分布；
- **社交窗口占比**：任意一条候选和任意一个邻居的 DCA < 1.0 m 的窗口；
- **候选条件化的程度**：在社交窗口里，20 条候选选出的邻居集合不全相同的比例。如果几乎全相同，C3 实际上就退化成按距离选，C3 和 C4 的差异会很小；
- 以上按 stable / transition / change、decel_stop 分组报告，再加一组"社交 / 非社交"。

## 5. 指标

- **主指标**：dev minADE20、minFDE20，3 seed 平均，与 A0 按 seed 配对比较。
- 分组：
  - 社交窗口 vs 非社交窗口，这是判断机制是否真起作用的关键；
  - stable / transition / change；decel_stop。
- 保护指标：Top1 FDE；未覆盖率（minFDE > 0.4 m）；平均修正幅度。
- 成本：修正模块注册参数量和有梯度参数量；CPU batch-1 下修正模块耗时，含风险计算和选邻居。

**训练后的检查（不训练新模型）：**
- **邻居置乱检查**：在 dev 上把 C2、C3、C4 的邻居 token 和邻居几何整体换成另一个窗口的，邻居数量保持一致。如果收益真的来自社交信息，置乱后应该回落到接近 C1 的水平。
- **未来置乱检查**：与上次相同。置乱真值不能改变模块的输出、选出的邻居或得分。

## 6. 预注册判定（运行前固定）

**记号：**
- g(X 相对 Y) = (Y − X) / Y，按 seed 配对后取平均；
- σ = A1 相对 A0 三个 seed 的 minFDE 改善的标准差；thr = max(0.5%, 2σ)；
- R = A1 和 A1L 中 dev minFDE 更好的那个，作为"无额外信息"的参照，避免把容量效应算成信息效应。

**为什么冻结底座下要求 3%：** E3_self 在冻结底座上是 +1.29%，端到端是 +2.2%，比值约 1.7。冻结底座下 ≥ 3%，才大致对应端到端 5% 的目标。这只是粗略换算，不是保证。

| 检查 | 内容 |
|---|---|
| P0 代理有效性 | A1 相对 A0 ≥ +0.8%，且和上次的 +1.29% 相差不超过 0.3 个百分点。不满足就判 PROXY_INVALID，停止 |
| Q1 历史细节 | C1 相对 R |
| Q2 社交上限 | C2 相对 R |
| Q3 本设计 | C3 相对 R，以及 C3 相对 A0 |
| Q4 风险选择 vs 距离选择 | C3 相对 C4 |
| Q5 稀疏 vs 稠密 | C3 相对 C2（只报告，同时比较成本） |
| 机制一致性 | C3 的收益应主要出现在社交窗口；邻居置乱后 C3 的收益应明显回落 |

所有"有效"都要求 minFDE 改善 ≥ 门槛，同时 minADE 改善 ≥ −0.2%。

**结论分五档：**
- **DESIGN_PROMISING**：同时满足
  - C3 相对 A0 ≥ +3.0%；
  - C3 相对 R ≥ +1.5%；
  - C3 相对 C4 ≥ thr；
  - 机制一致性成立；
  - 保护门通过。

  说明设计有希望达到 5%，下一步做端到端五折验证。
- **INFO_YES_DESIGN_NO**：C1、C2、C3 中至少有一个相对 R ≥ +1.5%，但 C3 相对 C4 < thr，或机制一致性不成立。说明解码器确实缺信息，但"按候选路径风险选邻居"不是关键。创新点要从"给解码器什么信息"重新设计。
- **INFO_SMALL**：最好的 C 臂相对 R 在 [thr, 1.5%) 之间。有一点信息增益，但在这个接口下很难到 5%。
- **NO_INFO_GAIN**：所有 C 臂相对 R 都 < thr。解码器不缺信息，现有接口下解码器到 5% 的可能性很低，需要讨论更换编码和解码之间的接口方式。
- **PROXY_INVALID**：P0 不通过。

**保护门**（只对被判为有效的臂检查）：
- Top1 FDE 相对 A0 变差不超过 2%；
- stable 组和 decel_stop 组的 minFDE 相对 R 变差不超过 1%；
- 成本：
  - C3 修正模块的 CPU batch-1 耗时比 A1 多出不超过 2 ms；
  - 修正模块总参数不超过 B0 的 10%，约 29.5k。

保护门不通过时，结论档位不变，但标注 PROTECTION_FAILED，并且不进入下一步。

## 8. 局限

1. 冻结底座只是代理。上次的实验已说明它对"自我修正"给出的信号方向和端到端一致，但对"读取新信息"类改动是否同样可靠，还不知道。
2. 只用了一个底座 seed，dev 被反复使用。
3. 邻居按匀速外推，而真实邻居也会变速、转向。风险估计在拥挤场景可能不准，这正是 C2（稠密、无外推）作为对照的意义。
4. 风险是用第一遍、修正前的候选路径算的，修正之后不再重新计算。这是为了保持单次前向、低成本。
5. ETH/UCY 很多场景人很稀疏，HOTEL、ZARA02 有约一半的窗口几乎是静止的人。社交收益在平均指标上可能被稀释，所以分组结果比平均值更能说明机制是否有效。
6. 邻居只读最后一步的 token。邻居的历史细节没有直接提供，不过编码器 token 已经包含了时间和社交混合后的信息。
